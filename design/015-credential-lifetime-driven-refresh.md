## Summary

Generators that mint time-limited credentials know when what they produced stops working.
Nothing in ESO acts on that knowledge: regeneration is scheduled solely from
`spec.refreshInterval`, a number the user picks without being able to see the lifetime it
has to stay under. When the two disagree the Secret holds an expired credential until the
next tick.

This proposal adds an optional way for a generator to report the expiry of the payload it
just returned, and makes the reconciler requeue at whichever comes first — the refresh
interval, or shortly before that expiry. Generators that report nothing keep today's
behaviour exactly.

## Motivation

[#6690](https://github.com/external-secrets/external-secrets/issues/6690) is the concrete
case. A `GCRAccessToken` generator using workload identity federation mints a token that
lives ~15 minutes, because the projected ServiceAccount token TTL is hardcoded to 900s and
STS caps the access token at the subject token's expiry. With `refreshInterval: 1h` the
Secret carries a dead token for 45 of every 60 minutes. The generator already returns an
`expiry` value — as data, in the output map, where nothing consumes it.

This is not one generator's oversight. It is the shape of the whole family: a generator
whose product is a short-lived credential has a lifetime, and ESO has no channel to learn
it. At least eight in-tree generators mint time-limited credentials
(`beyondtrustworkloadcredentials`, `cloudsmith`, `ecr`, `gcr`, `github`, `gitlab`, `quay`,
`sts`), and each is one hardcoded TTL away from the same report.

The workaround documented today — lower `refreshInterval` until it fits — asks the user to
guess a number that is neither exposed nor stable. In the WIF case above it is not even
user-controlled: it is a constant in ESO's own source.

### Goals

- A credential generated by ESO is regenerated before it expires, without the user having
  to discover and track its lifetime by hand.
- Generators opt in. An existing generator that is not updated behaves exactly as it does
  today, with no code change.
- The expiry a generator reports is visible to the user, so "when does this rotate" is
  answerable without reading provider documentation.

### Non-Goals

- Changing `refreshInterval` semantics for `SecretStore`-backed ExternalSecrets. This
  proposal touches only sources that go through a generator.
- Correcting individual generators' hardcoded TTLs. #6690 has a narrow fix of its own; this
  proposal is about the missing mechanism, and the two are independent.
- Guaranteeing a credential is never briefly invalid. Clock skew between ESO, the apiserver
  and the provider makes that unachievable; the goal is to remove the systematic multi-minute
  window, not to reach zero.
- Revoking the superseded credential. Cleanup of previous credentials stays where it is
  today, with `Cleanup` and `GeneratorState`.

## Proposal

A generator that knows its output's expiry says so as part of returning it. The reconciler
schedules the next reconcile at `min(refreshInterval, expiry - margin)`.

### API

The `Generator` interface is unchanged. A second, optional interface carries the expiry, so
the eighteen existing implementations compile and behave as before:

```go
// ExpiringGenerator is implemented by generators whose output stops being valid at a known
// point in time. The reconciler uses the reported expiry to schedule regeneration before
// the credential dies, instead of relying on refreshInterval alone.
type ExpiringGenerator interface {
	Generator

	// GenerateWithExpiry behaves exactly like Generate and additionally reports when the
	// returned payload stops being valid. A nil expiry means "not known for this call" and
	// is not an error: the reconciler then falls back to refreshInterval.
	GenerateWithExpiry(
		ctx context.Context,
		obj *apiextensions.JSON,
		kube client.Client,
		namespace string,
	) (map[string][]byte, GeneratorProviderState, *metav1.Time, error)
}
```

The expiry is returned by the call rather than read from the generator afterwards, because
generators are registered once as singletons (`genv1alpha1.Register(kind, NewGenerator())`)
and shared across every ExternalSecret in the cluster. Per-instance state would be a data
race dressed as an API.

The resolver type-asserts and prefers the richer call:

```go
if eg, ok := gen.(genv1alpha1.ExpiringGenerator); ok {
	data, state, expiresAt, err = eg.GenerateWithExpiry(ctx, obj, kube, ns)
} else {
	data, state, err = gen.Generate(ctx, obj, kube, ns)
}
```

The reported expiry surfaces on the ExternalSecret so a user can see it:

```yaml
status:
  refreshTime: "2026-08-08T10:00:00Z"
  generatedCredentialExpiresAt: "2026-08-08T10:15:00Z"   # new, optional
```

This is an additive status field. `apis/externalsecrets/v1` is frozen by default, so it is
called out here explicitly rather than slipped in: the alternative of keeping the expiry
only in memory is described under Alternatives, with the trade-off.

### User Stories

*As an operator registering a fleet of clusters in Argo CD*, I replace long-lived
ServiceAccount token Secrets with generated short-lived tokens, and I do not want to
discover the apiserver's maximum token lifetime in order to pick a refresh interval that
happens to sit under it.

*As a user of the GCR generator with workload identity federation*, I set
`refreshInterval: 1h` because that is what our other ExternalSecrets use, and I expect ESO
either to keep the token alive or to tell me it cannot.

*As a maintainer reviewing a new generator*, I want the expiry mechanism to be optional, so
that a generator whose output does not expire carries no ceremony for it.

### Behavior

Let `L` be the reported expiry and `R` the refresh interval.

- **`L` is nil** — today's behaviour, requeue after `R`. This is the path every existing
  generator takes.
- **`L - margin` is sooner than the next `R` tick** — requeue at `L - margin`. The margin is
  `max(30s, 10% of the remaining lifetime)`, so a 15-minute token refreshes at ~13.5 minutes
  and a 1-hour token at ~54 minutes.
- **`L` is already in the past** — regenerate on this pass, but subject to a floor
  (proposed: 30s) so a provider that returns a stale expiry cannot spin the reconciler. Set
  a condition rather than looping silently.
- **`L` is absurdly far out** — no special case; `R` wins, since `min` already covers it.
- **`R <= 0`** ("never refresh", an explicit user choice) — honour it. Do not override an
  explicit instruction, but set a condition saying the credential will expire at `L` and is
  not being renewed, because the silent version of this is the bug we are fixing.
- **The generator reports an expiry shorter than the margin floor** — refresh at once and
  set a condition; a credential that lives 20 seconds cannot be kept alive by any schedule
  and the user needs to be told, not served a hot loop.

`PushSecret` has the same shape and the same defect. Its reconciler should receive the same
treatment; if reviewers prefer, that can land as a follow-up rather than in one change.

### Drawbacks

- **Two ways to write a generator.** An optional interface is the price of not breaking
  eighteen implementations at once, but it does mean a contributor must know which one to
  implement. Mitigated by documenting `ExpiringGenerator` as the default choice for anything
  that mints a credential.
- **A write to the frozen v1 API.** Additive and status-only, but it is a v1 write and
  deserves an explicit decision rather than being treated as routine.
- **Trust in the reported value.** A generator that reports a wrong expiry now degrades
  scheduling as well as data. The floor and the conditions bound the damage but do not
  remove it.
- **More reconciles.** Short-lived credentials will requeue more often than the user's
  `refreshInterval` suggests, which is the point, but it is a real increase in API traffic
  and provider calls that a cluster admin should be able to see coming.

### Acceptance Criteria

**Rollout and rollback.** Ship behind a feature flag, consistent with
`014-feature-flag-consolidation`. Disabled, the resolver never takes the
`ExpiringGenerator` branch and behaviour is bit-for-bit today's. That makes rollback a flag
flip rather than a downgrade, which matters because the failure mode being introduced —
refreshing too often — costs provider quota.

**Test roadmap.**
- Unit tests for the schedule computation: nil expiry, expiry beyond `R`, expiry inside `R`,
  expiry in the past, expiry under the floor, `R <= 0`.
- envtest coverage in `pkg/controllers/externalsecret`, where the controller suites already
  live, asserting the requeue actually shortens and that the Secret is rewritten before the
  reported expiry.
- One generator converted as the worked example, with a test showing the reported expiry
  reaches the status field.

**Observability.** `status.generatedCredentialExpiresAt` answers "when does this rotate".
A counter for regenerations triggered by expiry rather than by interval tells an operator
how often the mechanism is actually doing something.

**Monitoring.** The useful alert is "a Secret managed by ESO holds a credential whose
reported expiry has passed" — computable from the new status field without provider
knowledge. Today the same alert is not expressible.

**Troubleshooting.** The failure modes a user will hit: the generator does not implement the
interface (status field absent — expected, not a fault); the provider caps the lifetime
below what was asked (reported expiry shorter than requested, condition explains it); the
credential is rejected despite being fresh (not this mechanism — points at the provider).

## Alternatives

**Keep the expiry in memory and never persist it.** Simpler: no v1 status field, no CRD
regeneration. The requeue is computed in the same reconcile that generated the payload. It
fails when the ExternalSecret is reconciled for an unrelated reason without regenerating —
the schedule silently reverts to `refreshInterval` — and it gives the user nothing to look
at. Worth taking if reviewers judge the v1 write too expensive; the mechanism still works
for the common path.

**A well-known key in the returned data map**, e.g. `expirationTimestamp`, read by the
reconciler. Requires no interface change at all, which is its whole appeal. Rejected as the
primary proposal because it is stringly-typed, collides with the user-facing key namespace
(a user templating `expirationTimestamp` would find it load-bearing), and gives no way to
say "I do not know" distinct from "I did not set that key".

**Fix each generator's TTL individually.** This is #6690's own fix and should happen
regardless. It does not address the mechanism: the next generator with a provider-capped
lifetime reproduces the report, and lifetimes that are genuinely short by nature — an STS
session, a registry token — cannot be lengthened at all.

**Let the generator shorten `refreshInterval`.** It cannot: `refreshInterval` belongs to the
ExternalSecret that references the generator, and a namespaced generator may be referenced
by many. Writing to them from the generator inverts ownership.

**Document the requirement and leave it to users.** The status quo. It asks the user to
know a number that ESO hardcodes in its own source, and in the WIF case there is no value of
`refreshInterval` that is both correct and stable across an upgrade that changes the
constant.
